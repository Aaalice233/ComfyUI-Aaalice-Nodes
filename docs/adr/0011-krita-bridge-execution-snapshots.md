# ADR 0011：Krita Bridge 使用短请求快照与显式失败

- 状态：Accepted
- 日期：2026-07-20

## 背景

`FetchFromKrita` 需要在工作流真正执行时读取 Krita 当前活动文档，而不是保存一个容易失效的文件路径、界面预览或工作流内图像副本。当前工作方式由用户先在 Krita 中准备文档和选区，再回到 ComfyUI 执行，因此 Bridge 只需要承担单向快照获取，不需要反向发送或双向编辑会话。

## 决定

1. 随包提供独立插件 `aaalice_comfy_bridge`。首次安装和异常修复由用户在共享 Krita 设置中显式触发，并同时原子写入 Krita 的插件启用项；已安装且版本低于随包版本时，由 ComfyUI 在启动和状态刷新边界自动以跨进程文件锁、锁内版本复核、同目录暂存、替换和失败回滚方式更新插件文件；回滚本身受系统阻止时保留恢复目录并持续显式报告，直到后续自动重试成功或显式修复完成后安全清理，不改变用户原有启用意图，也不自动安装缺失插件或降级更高版本。更新前写入跨 ComfyUI 重启保留的待确认标记；Krita 运行中可以先更新磁盘文件，但界面必须明确要求重启 Krita，直到观察到 Krita 已停止或目标 Bridge 版本已响应后才清除标记；节点不启动、关闭或定位 Krita。
2. ComfyUI 与 Krita 只通过专用临时目录交换原子 JSON 和请求专属 PNG，不开放本地端口。请求和响应都携带协议版本与唯一 `request_id`，Bridge 生成的快照媒体路径必须落在临时目录内。
3. `FetchFromKrita` 是零输入外部源节点。每次执行创建一个 `fetch_snapshot` 请求：Bridge 必须在 15 秒内以原子的 `processing` 响应确认接单，随后同步刷新 Krita 当前投影，并在独立的 120 秒期限内完成合成图和选区导出；完成、失败、超时或取消后只清理本次请求的数据。这样不会把已接单但仍在合成复杂文档误判为 Bridge 无响应。
4. 没有选区与合法全黑选区是不同状态：前者生成同尺寸全黑 `MASK`，后者保留 Krita 实际导出的全黑选区及“选区存在”元数据。
5. 活动文档若直接打开自 PNG/JPEG/WebP，Bridge 在本次最终响应中附带原文件路径；ComfyUI 立即读取其 A1111 `parameters` 并输出版本化 `METADATA`。路径不进入工作流或元数据载荷；未保存文档、`.kra` 或无参数原图输出显式空元数据。该可选字段保持协议 v1 向后兼容；两阶段响应与同步投影保持协议 v1 字段兼容，Bridge 实现版本升至 1.2.0。
6. Krita 未运行、Bridge 缺失或不兼容、没有活动文档、导出失败、路径或尺寸校验失败、声明的原文件消失或元数据损坏以及超时都使节点明确失败，不返回空图、旧快照或其它备用值。
7. Bridge 状态与最近一次执行摘要只用于界面反馈，不进入 `node.properties` 或工作流 JSON，也不能代替执行时重新读取。前端在每次 `queuePrompt` 开始时先合并执行一次状态刷新并清除节点上的旧执行摘要；刷新失败只在节点上显式反馈，不阻止后端按快照协议执行并返回更准确的实际错误。

## 影响

- `FetchFromKrita` 的结果不可缓存；V3 节点使用外部状态失效标记保证每次排队都重新请求。
- 短文件协议允许并发节点按请求身份隔离，也避免常驻网络服务和端口配置。
- 用户只需显式完成首次安装；后续随包 Bridge 升级自动应用。自动更新不改 Krita 配置，运行中的 Krita 会继续使用内存中的旧版本并收到一次明确重启提示；只有显式安装、启用或修复需要先关闭 Krita。
- 当前能力只面向同一台机器上的一个活动文档，不提供文档选择、批量抓取、图层选择、Krita 启动或双向编辑会话。
- 已安装 Bridge 1.0.0/1.1.0 仍能处理协议 v1 请求；更新本包并重启 ComfyUI 后会自动把磁盘安装升级到 1.2.0，若 Krita 当时正在运行，只需按界面提示重启 Krita 以加载新版。
